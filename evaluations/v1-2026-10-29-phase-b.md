# Phase B evaluation, 2026-10-29: two held-out scenarios

Roadmap item B7. Does Phase B (typed notes, people and aliases, coming up, role-play memory, tidy notes) make the plugin better at remembering a person? Status: **completed**, one run per arm.

## Result

Two new scenarios were written by a separate agent that had seen only the earlier scenarios' format, not the Phase B code. Each has 11 scored cases spread over 31 or 32 sessions, with 20 unrelated filler sessions in between. Replies were scored blind (pass 1, partial 0.5) by a reviewer that saw only the ground truth and the four replies with shuffled labels.

| Arm | Scenario D (11) | Scenario E (11) | Total (22) |
| --- | --- | --- | --- |
| Plugin now (`P`) | 8.5 | 10 | **18.5** |
| Full history (`F`) | 8 | 10 | **18** |
| Plugin before Phase B (`O`) | 5.5 | 9 | **14.5** |
| No memory (`N`) | 4 | 3.5 | **7.5** |

By behaviour, over both scenarios:

| Behaviour (cases) | P | O | F | N |
| --- | --- | --- | --- | --- |
| Plan versus done (4) | 3 | 2 | 3.5 | 0 |
| Aliases and similar names (6) | 5 | 3.5 | 4.5 | 3 |
| Coming up this week (2) | 2 | 1 | 2 | 0 |
| The agent's own promises (5) | 3.5 | 3.5 | 4 | 0 |
| Role-play kept apart from real life (5) | 5 | 4.5 | 4 | 4.5 |

- Phase B raised the plugin from 14.5 to 18.5 of 22, level with putting the whole history in the prompt (18). The gains are in aliases, coming-up and plan-versus-done. Promises did not change (3.5 both).
- The plugin used 1.12 million prompt tokens over the two scenarios, against 1.60 million for full history (70%). These histories are short (31 or 32 sessions). Full history grows with every session, while the plugin's context is capped at about 9,500 characters at session start plus recall per message.
- No memory still passes role-play cases, because not leaking real life is easy when nothing is remembered. Those cases matter for the memory arms.

## What failed

- **D01, a promise to follow up (all four arms failed).** On March 16 the user asked to be checked with "next week" about whether the boiler was fixed. The current plugin saved this as an `agent_commitment` note, and on March 28 the coming-up block listed it as overdue. The host still answered only the meal-planning request. Memory supplied the promise, but the host model did not act on it.
- **D04, a text to Mags.** The plugin picked the right Mags (the aunt, not the boss Maggie). Its draft treated the aunt's mid-June cruise as already over in May; the old plugin made the same mistake. Full history and no memory passed.
- **E08 and E10 (partial).** The ski-school reminder in E08 gave no amount or due date. E10 flagged the unconfirmed passport but invented a June conversation about travel insurance.
- **D11 (partial).** The plugin said the June 13–14 weekend was free, but did not say why (the Inverness visit was cancelled).

These were found on held-out data, so any change made in response must be checked on new scenarios.

## Method

- **Harness**: [`v1-2026-10-29-phase-b-harness.py`](v1-2026-10-29-phase-b-harness.py) and [blinding](v1-2026-10-29-phase-b-blind.py). The scenarios are [D](v1-2026-10-29-phase-b-scenario-d.py) (Ingrid, a pharmacist in Edinburgh) and [E](v1-2026-10-29-phase-b-scenario-e.py) (Tina, an architect in Melbourne). Every session in `SESSIONS_LONG` was run in order.
- **Host**: DeepSeek-V4-Pro with thinking enabled, the same model for every arm. The scenario's date is given to the host, as Claude Code gives the current date.
- **Plugin arms (P and O)**: each ran its own embedded installation with the local embedding model. Each arm called its version's own hook functions: `session_context` at session start, `prompt_context` before each message and `finish_turn` after each reply. The host got that version's MCP tools: `memory_recall`, `memory_note`, `memory_pause` and `memory_resume`, with their own descriptions and schemas. The version's skill text was in the system prompt. Tool calls and results stayed in the session transcript, as in Claude Code.
  - P is this branch. Role-play sessions used the role-play memory, as a bot sets it through the proxy header.
  - O is commit `8193859` (after A5 and A6, before B1). It has no role-play memory, so role-play sessions went into the same memory. It ran from a separate environment, so its memory service also ran the old code.
  - P's coming-up block used the scenario date. Stored messages carry the run's real date, since the service sets it; the scenario's own text states each session's date.
- **Full history (F)**: every earlier session's messages in the prompt. **No memory (N)**: the current session only.
- **Scoring**: one fresh reviewer per scenario read only the [blinded sheet](v1-2026-10-29-phase-b.evidence.tar.gz) (ground truth, criteria, user message, four replies with labels shuffled per case) and wrote verdicts before the sealed mapping was opened.
- **Evidence**: the archive holds every arm's per-turn results (inputs, replies, session context, tool calls and results, usage), the blinded sheets, the sealed mappings and the verdicts.

## Limits

- One run per arm with one host model, and one reviewer per scenario. A single case moves a total by up to one point. The reviewer flagged five verdicts that could reasonably be a step higher or lower.
- Short histories. At 31 or 32 sessions the full history still fits easily, so the scenarios test whether memory finds the right fact, not whether it beats full history on length.
- Each scenario has only two coming-up cases, and the behaviour totals are small.
- Claude has not been run as host. The roadmap asks for it.
- PersonaMem was not run.
